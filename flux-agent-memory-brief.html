02

Gap Analysis — Brain vs Flux Agent

Lo que el sistema brain/Engram tiene que Flux Agent no tiene (o tiene parcialmente)

Dimensión Flux Agent — hoy Brain/Engram — referencia Gap
Captura proactiva NO Pasiva total — indexa todos los turnos sin distinción. Decisiones importantes se pierden en ruido de tool calls. CLAUDE.md define CUÁNDO guardar. mem_save se llama explícitamente después de decisiones, bugs, discoveries. Protocolo obligatorio. El agente no sabe qué vale la pena preservar. No hay protocolo.
Evolución de memoria NO Append-only puro. Cada turno genera nuevos chunks. Si "vamos con Vue" reemplaza "vamos con React", ambas versiones coexisten. topic_key + upsert: el mismo "topic" actualiza el mismo row, revision_count++. Una decisión que evoluciona = 1 fila, N revisiones. Stale memories nunca mueren. Recall puede retornar decisiones contradictorias.
Herramientas explícitas NO get_tool_schemas() retorna []. El modelo no puede buscar ni guardar memoria explícitamente. Solo los providers externos tienen tools. 15 tools: mem_save, mem_search, mem_timeline, mem_get_observation, mem_context, mem_session_summary, etc. El agente es actor activo de su memoria. El agente es pasivo. No puede afirmar "recuerda que usamos X" ni buscar decisiones previas bajo demanda.
Búsqueda de corpus NO prefetch() solo busca en lo que el propio agente generó (turns + tool_results). No busca en el codebase, docs, ni graphify. brain-context.py hook: keywords → graphify graph.json + grep vault → inyecta ANTES del prompt. Contexto automático del corpus completo. El agente no recuerda arquitectura documentada ni decisiones que están en código/docs, solo sus propias conversaciones.
Lifecycle de memoria NO No hay soft-delete. Los chunks son permanentes. No hay forma de marcar una memoria como obsoleta. deleted_at soft-delete en todos los observaciones. mem_search filtra WHERE deleted_at IS NULL. Hard-delete disponible como opción explícita. La memoria crece infinitamente sin poda. Memorias obsoletas confunden el recall.
Resumen de sesión PARCIAL on_session_end() existe en MemoryProvider pero NativeMemoryProvider no lo implementa. Solo on_pre_compress extrae facts. mem_session_summary es un ritual explícito: Goal, Discoveries, Accomplished, Next Steps, Relevant Files. Se guarda como observación type='session_summary'. No hay cierre estructurado. La historia de lo que se hizo en una sesión no está disponible en futuras sesiones.
Memoria de delegación NO on_delegation() existe en MemoryManager pero NativeMemoryProvider no lo overridea. Los resultados de subagentes se pierden. SubagentStop hook: persiste memoria del subagente en la DB principal del parent. El orquestador sabe qué delegó y qué resultó. El orquestador pierde el resultado del trabajo delegado. Contexto del ejército de agentes no se acumula.
Scope de memoria PARCIAL Solo project scope implícito via session_id. No hay separación entre memorias del workspace vs memorias de preferencias del usuario. scope field en observations: "project" (workspace-specific) vs "personal" (cross-project user prefs). mem_search puede filtrar por scope. Una preferencia del usuario ("siempre usa tabs") mezcla con datos del proyecto ("usamos Django"). Imposible de aislar.
Diferencia fundamental
Flux Agent hoy
La memoria captura todo automáticamente pero no sabe qué importa. El ruido crece con el tiempo. El recall puede ser irrelevante o contradictorio.
Brain (target state)
La memoria captura lo que importa por protocolo + todo el corpus por graphify. El agente es actor activo. La memoria evoluciona y se poda.

Feature Proposals

8 mejoras — ordenadas por prioridad (P1=crítica, P2=alta, P3=mejora)

F1
Proactive Memory Protocol
P1 · Crítico NativeMemoryProvider system_prompt_block()
El mayor gap del sistema: el agente captura todo pero no sabe qué vale la pena preservar. Agregar un protocolo explícito en system_prompt_block() que le diga al agente cuándo llamar memory_save() y qué tipo asignar. Sin esto, todas las demás mejoras de memoria son ruido sin señal — el agente no cultivará su memoria, solo la acumulará.
What to add — en NativeMemoryProvider.system_prompt_block():
→ Reglas de cuándo save: después de decisión arquitectónica, bug resuelto, convención establecida, preferencia del usuario
→ Tipos canónicos: decision · bugfix · convention · preference · session_summary
→ Self-check tras cada tarea: "¿Decidí algo? ¿Resolví algo no obvio? Si sí → memory_save()"

Explicit Memory Tools — save, search, recall
P1 · Crítico NativeMemoryProvider.get_tool_schemas() 3 tools mínimas
NativeMemoryProvider.get_tool_schemas() retorna []. El agente no puede explícitamente guardar decisiones, buscar historia, ni actualizar un topic. Solo los providers externos de pago tienen esta capacidad. Agregar 3 tools mínimas al provider builtin: memory_save (con type y topic_key), memory_search (query sobre chunks y facts), memory_recall (por topic_key exacto).
Tools a implementar en NativeMemoryProvider:
memory_save(content, type, topic_key?) → INSERT o upsert si topic_key existe
memory_search(query, limit=5) → BM25 + fact lookup compacto
memory_recall(topic_key) → fetch exacto por topic_key, full content
handle_tool_call(): router hacia las 3 operaciones en NativeMemory

F3
Topic-key Upsert + Memory Evolution
P1 · Crítico BM25Layer schema topic_key + revision_count
La memoria actual es append-only. Si una decisión se revisa, coexisten versiones contradictorias. El principal mecanismo del sistema Brain es el topic_key upsert: un identificador semántico que permite que "la decisión de arquitectura de X" sea siempre 1 fila, N revisiones. Elimina el ruido de chunks redundantes y garantiza que el recall retorne la versión más reciente.
Schema change en memory_chunks:
+ topic_key TEXT (nullable, unique por project+scope)
+ revision_count INTEGER DEFAULT 1
+ deleted_at REAL (soft-delete)
BM25Layer.index(): si chunk.topic_key existe → UPDATE content + revision_count++ en lugar de INSERT
BM25Layer.search(): añadir WHERE deleted_at IS NULL
Files: agent/native_memory.py — BM25Layer._ensure_tables(), .index(), .search()

F4
Session Summary — cierre estructurado
P2 · Alta NativeMemoryProvider.on_session_end() topic_key: sessions/summary
on_session_end() existe en el contrato MemoryProvider pero NativeMemoryProvider no lo implementa. El Brain tiene mem_session_summary como ritual explícito. Implementar un cierre de sesión estructurado que extraiga Goal / Discoveries / Accomplished / Next Steps y lo guarde como chunk type='session_summary' con topic_key por session_id. En futuras sesiones, este summary se inyecta como contexto histórico.
Implement NativeMemoryProvider.on_session_end(messages):
1. Extraer último assistant message + últimas N decisiones del WorkspaceStateLayer
2. Generar structured summary (sin llamada LLM — heurístico sobre workspace state)
3. memory_save(type='session_summary', topic_key=f'session/{session_id}/summary', content=summary)
Bonus: memory_save también agrega al session log opcional en OMNIWORKER_HOME/session-log.md
Files: agent/native_memory.py (NativeMemoryProvider), run_agent.py (wiring on_session_end)

F5
Graphify Corpus Search en prefetch
P2 · Alta NativeMemory.prefetch() graphify-out/graph.json
La diferencia más poderosa del Brain: brain-context.py busca en el corpus completo del vault (graphify graph.json + grep vault) antes de que el LLM procese el prompt. En Flux Agent, prefetch() solo busca turnos propios. Conectar la búsqueda de prefetch al knowledge graph graphify-out/ significa que el agente tiene contexto semántico del codebase completo desde el primer turno — sin necesitar volver a explorar.
Agregar GraphifyLayer opcional a NativeMemory:
1. En prefetch(): si graphify-out/graph.json existe → extraer keywords del query
2. Buscar nodos relevantes en graph.json (score por nombre + community + edges)
3. Retornar top 6 conceptos como "Known codebase concepts" block
4. Combinarlo con BM25 + facts en el output de prefetch()
Zero dependencies: leer graph.json directamente (JSON), no requiere graphify CLI en runtime
Files: agent/native_memory.py (nuevo GraphifyLayer), NativeMemory.prefetch()

F6
Delegation Memory — subagent result store
P2 · Alta NativeMemoryProvider.on_delegation() tipo: delegation_result
El orquestador de Flux Agent delega tareas a workers especializados. on_delegation() existe en el contrato MemoryManager pero NativeMemoryProvider no lo implementa — los resultados del ejército de agentes se pierden. Implementar este hook significa que el orquestador acumula historial de qué delegó, a qué agente, y qué resultó. Esencial para un sistema multi-agente con aprendizaje real.
Implement NativeMemoryProvider.on_delegation(task, result, child_session_id, **kwargs):
1. Crear chunk type='delegation_result' con task + result truncado
2. Metadata: {agent_type, child_session_id, timestamp}
3. topic_key = f'delegation/{child_session_id[:8]}' (upsert si mismo worker reintentó)
4. BM25.index(chunk) → disponible en futuras búsquedas del orquestador
Files: agent/native_memory.py (NativeMemoryProvider.on_delegation)

Memory Scope — project vs personal
P3 · Mejora BM25Layer schema scope field
Actualmente todas las memorias son project-scoped implícitamente. No hay forma de separar "prefiero tabs sobre espacios" (preferencia personal, cross-project) de "este proyecto usa Django 4.2" (dato del workspace). Agregar un scope field al schema permite que las preferencias personales persistan entre proyectos y las del workspace se aislen.
Schema: + scope TEXT DEFAULT 'project' en memory_chunks
memory_save(content, type, topic_key?, scope='project'|'personal')
prefetch(): buscar primero scope='personal' global, luego scope='project' del CWD
system_prompt_block(): separar workspace state de user preferences en la inyección
Files: agent/native_memory.py — BM25Layer schema + NativeMemory.prefetch()

Context Budget Adaptivo por plataforma
P3 · Mejora _MAX_INJECTED_TOKENS OMNIWORKER_MEMORY_TIMEOUT ref.
_MAX_INJECTED_TOKENS = 2000 es un valor hard-coded en native_memory.py. Para sesiones de código complejas necesita ser mayor; para plataformas gateway (Telegram, Discord) donde el contexto es caro, necesita ser menor. Siguiendo el patrón de OMNIWORKER_MEMORY_TIMEOUT (ya configurable via env var), hacer el budget adaptivo por plataforma y configurable.
Config: añadir memory.max_tokens_injected en config.yaml (default: 2000)
Platform overrides: cli=3000, gateway=1200, cron=500
NativeMemory.prefetch(): leer budget de config en lugar de constante
Env var fallback: OMNIWORKER_MEMORY_TOKENS (siguiendo el patrón existente)

Superficie de cambio
Las 8 features impactan principalmente agent/native_memory.py. El MemoryManager y el contrato MemoryProvider ya tienen todos los hooks necesarios (on_delegation, on_session_end, on_session_switch, on_pre_compress). Solo hay que implementarlos en NativeMemoryProvider.
Lo que NO cambiar
La arquitectura de MemoryManager + MemoryProvider + plugins externos está bien diseñada. No tocar la interfaz pública ni el sistema de plugins. Las mejoras van dentro del provider builtin, no alrededor de él.

upserts vs inserts
Session coverage
sesiones con summary / total
>90% = cierre consistente
