Patrón unificado de 2026
Todos los proyectos que están funcionando en 2026 convergen en lo mismo: agentes definidos como datos (JSON/YAML), modelo fijo por rol, daemon autónomo con task queue, skills como contexto comprimido inyectado, y el orquestador como capa de routing — no de ejecución. Ninguno usa routing dinámico de modelos mid-conversación. Todos tienen loop detection (máx 3 fallos → escalar).

Objetivo 01
El agente como orquestador real
El agente deja de ser un chat reactivo y pasa a ser un director de operaciones autónomo. Tiene iniciativa propia, detecta qué hay que hacer sin que el humano se lo diga, descompone tareas, delega a agentes especializados, y aprende de cada ciclo. El humano interactúa para dar dirección estratégica — no para activar cada tarea.

El orquestador consulta el registry y lanza el agente correcto para cada tarea. No hay routing dinámico — el modelo está determinado por el tipo de tarea desde el inicio.

Por qué esto NO es el routing dinámico que evitamos
La clasificación de complejidad la hace el orquestador una sola vez, antes del spawn, con contexto completo. El modelo asignado queda fijo durante toda la ejecución del general_agent — nunca cambia mid-task. El patrón malo (que el router viejo causaba y que el partner ya parchó) era cambiar de modelo a mitad de una tarea en curso, perdiendo contexto. Acá el general_agent es el único agente cuyo modelo se decide al spawn en vez de estar hardcodeado — todos los especialistas mantienen su modelo fijo del registry. Decisión 100% backend, encriptada, solo el orquestador.

Reescritura del system prompt del orquestador
El cambio más impactante y el más barato de implementar: cambiar el system prompt del agente principal de "asistente que ejecuta lo que se le pide" a "director de operaciones que decide y delega". El LLM cambia completamente su comportamiento con el prompt correcto. Basado en lo que encontramos en Mission Control, CORE y Praktor. 
# omniworker-agent/prompts/orchestrator.md

## Tu rol
Eres el Orquestador de OmniWorker. NO eres un asistente que ejecuta tareas.
Eres un Director de Operaciones que decide, planifica, y delega.

## Tu primera pregunta ante cualquier input
"¿Qué tipo de tarea es esta y qué agente especializado debería manejarla?"

## Jerarquía de decisiones
1. ANALIZAR: Entender el intent real detrás del input (no el literal)
2. DESCOMPONER: Si la tarea es compleja, crear subtareas en el kanban
3. CONSULTAR REGISTRY: Qué agente del registry maneja este tipo?
4. DELEGAR: Lanzar el agente correcto con un brief claro y acotado
5. INTEGRAR: Recibir el summary del agente (no el raw output) e integrar al plan
6. ACTUALIZAR: Actualizar el kanban con el progreso real
7. APRENDER: ¿Este patrón merece convertirse en un skill?

## Cuándo ejecutas tú directamente (excepciones)
- La tarea es una conversación simple (≤ 2 mensajes, ≤ 50 chars)
- El usuario pidió explícitamente que lo hagas tú
# REGLA: "no hay agente para esto" NO es excepción. → siempre delegar a general_agent.
# El orquestador NUNCA ejecuta tareas complejas directamente (context pollution).

## Cuándo tienes INICIATIVA PROPIA
- Si ves una tarea pendiente en el kanban sin asignar → asignarla y delegarla
- Si una tarea lleva > 24hs sin progreso → revisarla y reactivarla
- Si detectas un patrón repetido en 3+ tareas → proponer un skill
- Si el usuario compartió un objetivo → descomponer en tareas sin esperar

## Brief de delegación (qué incluir)
NO incluir: historial completo de conversación, contexto del orquestador
SÍ incluir: objetivo específico, contexto mínimo necesario, criterio de éxito, formato de output esperado
  • prompts/orchestrator.md — nuevo system prompt del agente principal
  • prompts/worker_base.md — template base para workers (brief + formato de output)
  • agent_init.py — leer el system_prompt del registry en lugar del hardcoded
  • No tocar context_compressor — el compañero lo está manejando

ALTO IMPACTO
Meta-loop autónomo (el daemon)
El orquestador necesita un loop propio que se ejecute sin input del humano. Basado exactamente en el patrón de Mission Control (daemon que pollea task queue) y Praktor (cron-style autonomous tasks). El daemon corre en background, lee el kanban, detecta tareas pendientes, y las delega al agente correcto. El humano puede darlo dirección estratégica — pero el agente no espera al humano para avanzar. 
# omniworker-agent/orchestrator_daemon.py
# Background loop — el corazón del orquestador autónomo

class OrchestratorDaemon:
    """
    Corre en background. Pollea el kanban cada N segundos.
    Si encuentra tareas pendientes → las delega al agente correcto.
    No necesita input del humano para avanzar.
    """

    POLL_INTERVAL = 30  # segundos entre polls
    MAX_FAILURES = 3   # loop detection — escalar tras 3 fallos
    CRON_TASKS = [
        {"schedule": "0 9 * * 1",   "task": "weekly_review"},      # Lunes 9am
        {"schedule": "0 8 * * *",   "task": "daily_standup"},      # Diario 8am
        {"schedule": "0 18 * * 5", "task": "autolearning_review"}, # Viernes 6pm
    ]

    async def run_forever(self):
        while True:
            await self.tick()
            await asyncio.sleep(self.POLL_INTERVAL)

    async def tick(self):
        # 1. Check cron tasks
        due_cron = self.get_due_cron_tasks()
        for task in due_cron:
            await self.dispatch_task(task)

        # 2. Poll kanban for unassigned ready tasks
        pending = self.kanban.get_ready_unassigned()
        for task in pending:
            agent_type = self.classify_task(task)
            await self.delegate(task, agent_type)

        # 3. Check stalled tasks (> 24h sin progreso)
        stalled = self.kanban.get_stalled(hours=24)
        for task in stalled:
            await self.reactivate_or_escalate(task)

    async def delegate(self, task, agent_type):
        config = get_agent_for_task(agent_type)  # del registry
        brief = build_brief(task)               # no el historial completo
        result = await run_worker_agent(config, brief)
        summary = extract_summary(result)        # no el raw output
        self.kanban.update_task(task.id, summary)
        self.check_autolearning_trigger(task, summary)

DIFERENCIADOR
Autolearning conectado al orquestador
El skills autolearning ya existe en OmniWorker — es el diferenciador más grande vs todos los competidores. Ningún framework open-source lo tiene. El paso que falta es conectarlo al orquestador para que se active automáticamente después de cada tarea completada exitosamente. La lógica: si una tarea se repite o se resuelve con un patrón identificable → el orquestador propone un skill. El skill se convierte en contexto comprimido (~50-650 tokens) inyectado en futuros workers. 
# Añadir a orchestrator_daemon.py

async def check_autolearning_trigger(self, task, summary):
    """
    Después de cada tarea exitosa: ¿merece convertirse en skill?
    Reglas:
      - Mismo patrón visto 3+ veces → proponer skill automáticamente
      - Tarea compleja resuelta con éxito → sugerir skill al orquestador
      - Intervalo: cada 30 tareas → review de autolearning
    """
    self.task_history.append(task)

    # Check: mismo tipo de tarea vista 3+ veces
    similar = [t for t in self.task_history
               if t.type == task.type]
    if len(similar) >= 3 and not self.skill_exists_for(task.type):
        await self.propose_skill(
            task_type=task.type,
            examples=similar[-3:],
            summary=summary
        )

    # Check: intervalo periódico (cada 30 tareas)
    if len(self.task_history) % 30 == 0:
        await self.autolearning_review()

async def propose_skill(self, task_type, examples, summary):
    # Lanzar skill_creator con el patrón detectado
    brief = build_skill_proposal_brief(task_type, examples, summary)
    await delegate(brief, agent_type="planner")
    # Notificar al usuario: "Creé un skill nuevo: {task_type}"
    await self.notify(f"Nuevo skill propuesto: {task_type}")

Conclusión estratégica
Con las 4 fases implementadas, OmniWorker no tiene competencia directa. Mission Control tiene el daemon, Praktor tiene el modelo fijo por agente, gentle-ai tiene el workflow — pero ninguno tiene las tres cosas juntas + skills autolearning + 20 plataformas + browser propio. El plan convierte a OmniWorker en el único sistema que combina runtime completo + orquestador autónomo + ejército especializado + aprendizaje continuo.

Gestión dinámica de modelos

Los providers lanzan modelos constantemente y deprecan otros. Este sistema permite que los agentes se actualicen automáticamente sin interrumpir el servicio, y sin que el usuario final vea nada.

Dos archivos, dos responsabilidades
# agent_types.yaml — LA CONSTITUCIÓN (toca el humano)
developer:
  model: glm-5           # modelo base definido al crear el agente
  fallback_model: glm-4-9b  # siempre disponible, estático
  model_family: glm      # para agrupación en auto-update

# model_overrides.yaml — CAPA DINÁMICA (toca el orquestador)
overrides:
  glm:
    active: glm-5
    previous: glm-4.9
    updated_at: 2026-06-10T08:00:00Z
    source: saas_daily_check

Resolución: el agente lee primero model_overrides.yaml, si no hay override lee agent_types.yaml. Nunca se rompe la config base.

Flujo completo de actualización
1. SaaS corre daily_model_check → pollea /models de cada provider
2. Detecta cambio: actualiza model_catalog en DB
3. Push al Smart Router (webhook / polling 5min)
4. Router notifica al Orquestador con { family, old, new, severity }
5a. Minor bump: orquestador activa fallback_model → escribe override → desactiva fallback
5b. Major change: orquestador activa fallback + notifica operador → espera aprobación
6. Agentes continúan sin interrupción durante toda la transición
Regla de oro del routing
Solo el orquestador llama al router. Los agentes worker nunca hacen llamadas al router ni conocen su modelo. El modelo se les asigna en el momento de ser spawneados y es fijo durante toda su ejecución. El orquestador consulta el router al inicio de cada sesión para verificar el estado del catálogo — no en cada delegación.
Notificación al operador (cambio mayor)
El "humano" notificado es el operador del SaaS (vos y tu socio), no el cliente final. La notificación llega al panel de admin: "GLM-6 disponible. Agentes afectados: developer, code_runner, marketer. ¿Actualizar ahora o en próxima ventana de mantenimiento?". El cliente nunca ve nada — su "Agente de Desarrollo" sigue funcionando con el fallback mientras tanto.
🔒

Capa de opacidad SaaS — el modelo es infraestructura

El cliente ve roles, no modelos. "Agente de Marketing está trabajando" — nunca "glm-5 está procesando". El modelo es infraestructura interna que puede cambiar sin que el producto cambie.

REGLA
Una sola regla de encriptación
Todo componente que comunica hacia el desktop, gateway, o front ejecuta strip_model_info() antes de enviar. Esta función se implementa una sola vez en el gateway como middleware — no en cada agente. Hacia adentro fluye info completa; hacia afuera nunca sale model, provider, ni base_url.
BLOQUE DISPLAY
Qué ve el usuario final
Cada agente en agent_types.yaml tiene un bloque display: con name e icon. El SaaS frontend solo consume esos campos. Los campos provider, model, fallback_model, base_url son infraestructura interna — nunca salen del backend.
"Agente de Marketing" — no "glm-5 via opencode-go"
BILLING
Costos reales vs precio al cliente
Los costos reales por token se registran internamente por tenant y por agente. El cliente ve unidades de negocio (tareas completadas, horas de agente, créditos). Si mañana Kimi lanza una versión más barata, cambiás el modelo en el YAML y mejorás tu margen sin que el cliente note nada. El producto es el agente, no el modelo.
4 Layers de autolearning — mapa completo
Layer Qué captura Creado por
Memory Contexto del usuario y estado actual Memory review (ya existe)
Skills HOW — procedimientos por clase de tarea Background review (ya existe)
Cron jobs WHEN — tareas recurrentes autónomas Pattern engine (ya existe)
Agent types WHO — qué rol/modelo maneja qué clase Orquestador con propuesta → humano aprueba (NUEVO)
Flujo de creación de agentes
1. general_agent recibe N usos del mismo tipo de tarea
2. Nudge dispara: orquestador analiza el patrón
3. Orquestador escribe draft en agent_types_proposals.yaml
    con: nombre, rol, model_family, toolset sugerido
4. Notifica al operador: "Propongo crear competitive_intel_agent"
5. Operador aprueba → orquestador mueve draft a agent_types.yaml
⚠️ El orquestador nunca crea agentes unilateralmente — siempre aprobación humana
